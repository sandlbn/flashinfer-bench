## Supported backends

FlashInfer-Bench addresses devices by string — `cuda:0`, `xpu:0`, `cpu`. Everything
backend-specific behind those strings lives in `flashinfer_bench.device`, so benchmark
and evaluator code contains no vendor branches.

| Backend | Device strings | Status | Kernel timing |
| --- | --- | --- | --- |
| NVIDIA CUDA | `cuda:N` | Supported | CUPTI activity tracing (device-side kernel duration) |
| Intel GPU (XPU) | `xpu:N` | In bring-up | Device events (includes launch overhead) |
| CPU | `cpu` | Reference and testing only | Host wall clock |

The CPU backend is not a benchmarking target. It exists so runners, evaluators and
validation gates can be exercised without a GPU, and so a reference implementation can
still run when an accelerator lacks an operator.

## Selecting a device

By default, the first available accelerator backend is used. Override it with
`FIB_DEVICE_BACKEND`:

```bash
FIB_DEVICE_BACKEND=xpu flashinfer-bench run
FIB_DEVICE_BACKEND=cpu flashinfer-bench run   # no GPU required
```

Naming a backend explicitly is honoured even when that backend is unavailable, so a
misconfigured environment fails with a clear error instead of silently benchmarking on
the CPU. The CLI's `--devices` flag takes device strings directly:

```bash
flashinfer-bench serve --local ./dataset --devices xpu:0,xpu:1
```

## Timing is not interchangeable between backends

A CUPTI trace reports device-side kernel duration. A device-event timer brackets the
launch as well. Those numbers are not comparable, so every trace records which timer
produced it in `evaluation.environment.libs.timing`.

<Warning>
Never compare latencies across backends without checking that field, and never compare a
solution's latency against a reference latency measured on different hardware. Leaderboard
results are grouped by hardware for this reason.
</Warning>

CUPTI timing requires `flashinfer-python`, which is an optional dependency:

```bash
pip install flashinfer-bench[cuda]
```

Without it, CUDA kernels are timed with device events and a warning is emitted — the
measurement still runs, but the methodology has changed.

## Comparing results across hardware

Speedup is measured against the definition's reference **on the same device**. That makes
a speedup meaningful within one device, and not transferable between two: 3× over a slow
Xe2 reference is not the same achievement as 3× over a fast Hopper reference, and the two
may not even have been timed the same way.

`get_best_trace` therefore refuses to rank traces that span multiple devices:

```python
ts.get_best_trace("rmsnorm_h4096")                              # raises if mixed
ts.get_best_trace("rmsnorm_h4096", hardware="INTEL_ARC_B580")   # ranks within one device
ts.hardware_ids("rmsnorm_h4096")                                # what is present
```

Pass `allow_mixed_hardware=True` only when you have established that the comparison is
valid.

### Per-hardware tolerances

Bringing up a new accelerator invites quietly loosening tolerances until things pass.
Hardware-specific tolerances therefore live in one reviewable place — the
`hardware_config` block of `eval_config.yaml`, keyed by canonical hardware id:

```yaml
hardware_config:
  INTEL_ARC_B580:
    # Justify every entry: say why the hardware genuinely differs, not that a test failed.
    rtol: 0.02
```

They override op-type and per-definition config, and are themselves overridden by CLI
flags. The achieved error stays recorded in `Correctness`, so a relaxation that is masking
a real bug remains visible.

## Definitions the hardware cannot run

A definition whose dtypes the device does not support is **skipped**, not benchmarked. Run
anyway, it either fails in a way that reads as a broken kernel, or lands on a silently
emulated path and gets timed as though it were native. Supported dtypes come from the
device's capability record; the run logs what it skipped and why.

This matters immediately on Xe2, which has no native FP8: FP8 definitions in the dataset
are reported as unsupported rather than as failures.

## Intel GPUs

Intel support targets Battlemage (Xe2-HPG, e.g. Arc B580) today, with Xe3P
"Crescent Island" as the next target. Both use the same software stack, so both are
served by one backend.

Install PyTorch with XPU support from Intel's wheel index:

```bash
pip install torch --index-url https://download.pytorch.org/whl/xpu
pip install flashinfer-bench
```

Verify the device is visible:

```python
>>> from flashinfer_bench.device import get_accelerator, list_devices
>>> list_devices()
['xpu:0']
>>> get_accelerator("xpu:0").canonical_id("xpu:0")
'INTEL_ARC_B580'
```

Triton solutions run on Intel GPUs through the Intel Triton backend
(`pytorch-triton-xpu`, installed alongside the XPU torch wheels) with no changes to the
solution. Native SYCL solutions are not yet supported.

## Bringing up a new device

Before benchmarking on hardware FlashInfer-Bench has not run on before, cross-validate the
reference implementations. A solution's correctness is judged against its definition's
PyTorch reference *running on the same device* — so if an operator is wrong, emulated, or
lower-precision on that backend, a wrong solution would validate against a wrong reference
and the error would be invisible.

```bash
flashinfer-bench validate-references --local ./dataset --device xpu:0 \
    --output attestation-b580.json
```

Each reference runs on the device and on the host with bit-identical inputs, and the
outputs are compared. The command exits non-zero if any definition fails, so CI can gate
on it. Definitions come back in one of these states:

| Status | Meaning |
| --- | --- |
| `PASSED` | Cleared for benchmarking on this device |
| `MISMATCH` | Device and host references disagree — do not benchmark |
| `UNSUPPORTED_DTYPE` | The device lacks a dtype the definition needs |
| `TARGET_ERROR` | The reference could not run on the device |
| `BASELINE_ERROR` | The reference could not run on the host either |
| `BUILD_ERROR` | The reference could not be built |
| `NO_WORKLOAD` | No workload in the dataset, so nothing was checked |

Anything other than `PASSED` quarantines the definition. A quarantined definition is not a
bug in the benchmark — it is the system declining to produce a number it cannot stand
behind.

<Note>
Workloads are hardware-independent. A workload captured from an SGLang run on an H100 is a
valid replay input on an Intel GPU, so bringing up new hardware never requires
re-collecting workloads.
</Note>

### First run compiles kernels

Intel's runtime compiles kernels to device code on first use and caches them under
`~/.cache/neo_compiler_cache`. On a cold cache that compilation takes minutes — long
enough, left inside a timed evaluation, to report a perfectly good solution as `TIMEOUT`.

Benchmark workers therefore warm the device up before signalling ready, so the cost is
paid once at startup and outside any timed or timeout-bounded region. Expect the first
run on a new machine to pause for a minute or two with a log line explaining why;
subsequent runs start in about a second.

### Warmup and measurement variance

Intel GPUs default to **200 warmup iterations** rather than the generic 10. Discrete Arc
parts ramp clocks from idle, and the first couple of hundred iterations run measurably
slower than the steady state. This is a default, so any config layer or `--warmup-runs`
still overrides it.

## Host power settings dominate everything else

Before trusting any measurement, put the host in a performance power profile. This matters
more than any benchmark parameter.

```bash
powerprofilesctl set performance    # or: echo performance > /sys/firmware/acpi/platform_profile
```

Measured on a laptop with an integrated Intel GPU, same kernel, same everything else —
run-to-run variation of the reported median:

| Platform profile | Variation (CV) | Behavior |
| --- | --- | --- |
| `performance` | ~1% | Stable; settles after ~40–80 iterations |
| `low-power` | ~40–50% | Sporadic ~2.8x excursions lasting hundreds of iterations |

The excursions are not GPU throttling — the GPU sits pinned at its maximum clock
throughout. It is the memory path being limited, which an integrated GPU depends on
entirely. Nothing in a trace records that the host was throttling, so a run under a
power-saving profile produces numbers that look ordinary and mean nothing. Benchmark
runners emit a warning at startup when they detect a throttling profile or battery power.

Once the host is in a performance profile, the warmup ramp becomes visible and behaves as
expected: latency settles within 2% of steady state after roughly 40–80 iterations, well
inside the 200-iteration default.

### Tensors reach workers through host memory

Benchmark workers are separate processes that receive baseline tensors over a pipe. CUDA
passes device tensors directly via IPC handles; torch has no equivalent for XPU, where
pickling one raises `_share_fd_: only available on CPU`. The XPU capability record
declares this, and baselines are copied through host memory for the crossing. The cost is
one round trip per workload, not per iteration, and devices that support IPC are
unaffected.

### Benchmarking against vLLM and SGLang kernels

The kernels vLLM and SGLang ship for Intel are the bar that matters — beating PyTorch eager
says little. Add them to a dataset as baselines and they are measured like any other
solution:

```bash
flashinfer-bench add-baselines --local ./dataset
FIB_DEVICE_BACKEND=xpu flashinfer-bench run --local ./dataset
```

Baselines match strictly on op_type and exact input/output names, so a signature near-miss
yields no baseline rather than a wrong comparison. Neither library is a dependency; when
absent, no baselines are offered.

### Adding a new Intel part

Most of the capability record comes from the driver, not from a table: cache size,
sub-group widths, shared local memory, EU counts, and whether the part has XMX/DPAS
matrix units are all read from `torch.xpu.get_device_properties` and recorded into the
trace. A part FlashInfer-Bench has never seen still works, with no SYCL target set, so
native kernels compile to SPIR-V and JIT at load time — the path that lets a device run
on the day it arrives.

`_PART_PROFILES` in `flashinfer_bench/device/xpu.py` only supplies what the driver cannot:
a fallback cache size and the ahead-of-time SYCL target triple.

Integrated parts often report a generic name — `Intel(R) Graphics` — which every such
device would collide on. Those are disambiguated by PCI device id, giving ids like
`INTEL_GRAPHICS_FD80`.
